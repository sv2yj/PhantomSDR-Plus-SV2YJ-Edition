# Панель администратора PhantomSDR-Plus — руководство по настройке

> ⚠️ **Замечание по безопасности:** держите эту панель администратора в домашней сети или за VPN. Публичное открытие административного порта не рекомендуется без надлежащего усиления аутентификации.

---

## Обзор

Панель администратора состоит из двух служб Python:

| Служба | Файл | Роль |
|---|---|---|
| Панель администратора | `admin_server.py` | Веб-приложение Flask, привязано к `127.0.0.1` (только внутренне) |
| Обратный прокси | `proxy.py` | Открывает и SDR, и панель администратора на одном публичном порту |

Обе службы читают конфигурацию из `admin_config.json`, который создаёт `setup_admin.sh`. **Не правьте константы портов прямо в файлах Python** — все порты и IP-адрес узла SDR хранятся в `admin_config.json`.

---

## Что даёт панель администратора

- **Панель мониторинга** — состояние сервера в реальном времени, ЦП/ОЗУ, основные процессы, свежий вывод журналов, терминал
- **Редактор конфигурации** — просмотр, правка и сохранение любого файла `.toml`, `.sh`, `.json`, `.h`, `.cpp` в вашей установке
- **Просмотр журналов** — слежение за любым журналом в реальном времени (сервер SDR, панель администратора, RADE, аварии, autorun, прокси)
- **Маркеры** — просмотр и правка частотных маркеров
- **История чата** — просмотр журнала чата WebSDR, полная очистка или удаление отдельных сообщений без перезапуска сервера
- **Сообщение на водопаде** — трансляция постоянного баннера всем подключённым пользователям, видимого на водопаде в реальном времени
- **Пользователи** — живой список подключённых слушателей с их частотой, режимом, длительностью и кнопкой ⚡ Kick
- **Удаление сообщений чата** — кнопка 🗑 Delete, немедленно убирающая из журнала именно это сообщение
- **Трансляция сообщений на водопад** — позволяет вывести постоянный текстовый баннер на водопад каждого подключённого пользователя
- **Spot Reporting** — запуск/остановка декодера autorun FT8/FT4/JS8/WSPR, выбор диапазонов/режимов и отправка спотов в PSK Reporter / wsprnet (по умолчанию выключено), с двумя счётчиками: плитки по декодерам за текущий запуск и итог за всё время рядом с каждым флажком диапазона/вида связи
- **Графики** — частота ЦП, загрузка ЦП, температура ЦП и подключённые пользователи за последние 15 минут / 1 час / 4 часа / 12 часов / 24 часа
- **Тепловая защита (Thermal Guard)** — останавливает сервер при перегреве процессора и запускает его снова, когда тот остынет; пороги выводятся из вашего собственного процессора. Работает с любым способом запуска и остановки и поставляется в режиме только записи, поэтому ничего не делает, пока вы её не включите
- **Настройки** — смена пароля администратора, базового каталога SDR, имени процесса, публичного порта

## Требования

- PhantomSDR-Plus уже установлен и работает
- Python 3.8+

> [!NOTE]
> **Обычно установщик делает это за вас.** `./install.sh` — как и каждый из четырёх установщиков для дистрибутивов, оба установщика RADE и установщик сервера статистики — настраивает панель по умолчанию, предварительно ставя `pip` менеджером пакетов системы, если его нет. На этой странице описано, что происходит на том шаге и что делать, если вы его пропустили или хотите что-то изменить позже.

Библиотеки Python для панели (`flask`, `psutil`, `aiohttp`, `tomli-w`) устанавливает `setup_admin.sh`; если это не удастся, он выведет точную команду для ручного запуска.

## Шаг 1 — Файлы

Поместите эти четыре файла в каталог PhantomSDR-Plus:

```
admin_server.py
manage_admin.sh
setup_admin.sh
proxy.py
```

Сделайте сценарии оболочки исполняемыми:

```bash
chmod +x setup_admin.sh manage_admin.sh
```

## Шаг 2 — Запустите сценарий настройки

```bash
./setup_admin.sh
```

Сценарий:

1. Проверит, установлен ли Python 3
2. Убедится в наличии `admin_server.py` и `manage_admin.sh`
3. Запишет `127.0.0.1` как `sdr_host` в конфигурацию (см. [Настройка `sdr_host`](#настройка-sdr_host))
4. Запросит три номера портов. Каждый запрос предлагает значение по умолчанию в скобках,
которое принимается простым Enter, так что обычная настройка — это три нажатия клавиш:
   - **Порт spectrumserver** — порт, на котором слушает ваш сервер SDR (по умолчанию `8900` —
     именно он прописан в каждом `config-*.toml` репозитория)
   - **Внутренний порт панели администратора** — где локально привязывается `admin_server.py` (по умолчанию `3000`)
   - **Публичный порт прокси** — единственный внешний порт, объединяющий SDR + администрирование (по умолчанию `8902`)

Неверные ответы отклоняются, и вопрос задаётся снова, но лишь пять раз — после этого берётся значение по умолчанию. Запуск, ввод которого не является терминалом (конвейер, cron, без присмотра), сразу берёт значения по умолчанию, вместо того чтобы ждать ввода, которого не будет.
5. Установит `flask`, `psutil`, `aiohttp` и `tomli-w` через pip
6. Предоставит `ss` возможность `cap_net_admin` (запасной путь функции отключения пользователей, нужен только если панель работает без прокси)
7. Спросит, какой сценарий запускает, а какой останавливает приёмник — через них панель управляет сервером, и тепловая защита тоже
8. Спросит, как далеко тепловая защита процессора может действовать сама — `log`, `throttle`, `stop` или `stop+restart` — и предложит запустить `setup-cpufreq-perms.sh`, чтобы этап throttle работал без root (см. [THERMAL_GUARD.md](THERMAL_GUARD.md))
9. Запишет `admin_config.json` со всеми настройками
10. Предложит установить два юнита systemd (панель + прокси) — запуск при загрузке и перезапуск после сбоя. **Рекомендуется и выбрано по умолчанию** (достаточно нажать Enter): защита от перегрева процессора работает только пока работает панель, поэтому без юнитов после перезагрузки машина остаётся без защиты. Шаг автоматически пропускается там, где systemd не является PID 1 (контейнеры, WSL1, OpenRC) или где нет sudo.

После настройки откройте браузер через прокси:
```
http://YOUR_SERVER_IP:<proxy_port>/admin
```
Пароль по умолчанию: **`admin`**

> ⚠️ **Немедленно смените пароль** — при первом входе перейдите в Settings. Мастер первого запуска проведёт вас через выбор каталога SDR, имени процесса, публичного порта и нового пароля.

## Шаг 3 — Запуск / остановка / перезапуск

Панель и прокси можно запускать двумя способами. **Выберите один и придерживайтесь его** — предупреждение в конце раздела объясняет, что будет, если их смешать.

> **Способ B (systemd) настоятельно рекомендуется** везде, где systemd доступен. Защита от перегрева процессора работает внутри панели, поэтому панель, умершая в 03:00, или перезагрузившаяся машина оставляют процессор без защиты, пока кто-нибудь не запустит её вручную. `setup_admin.sh` теперь предлагает юниты по умолчанию. Способ A используйте там, где systemd нет — контейнеры, WSL1, OpenRC/sysvinit — или когда вы сознательно хотите присматривать за всем сами.

### Способ A — `manage_admin.sh` (без root, ничего не устанавливается)

```bash
./manage_admin.sh start      # start admin panel and proxy
./manage_admin.sh stop       # stop both
./manage_admin.sh status     # show running status and PIDs
```

Команды **`restart` намеренно нет**. Раньше она убивала панель и тут же запускала собственную копию, что конфликтует с systemd на любой машине со Способом B. Чтобы перезапустить по Способу A, выполните `stop`, затем `start` — см. [Перезапуск панели](#перезапуск-панели) ниже.

Один сценарий управляет **обоими** процессами. Перед запуском прокси он проверяет, установлен ли `aiohttp`, и при отсутствии выводит понятную ошибку с командой исправления.

Ничего не запускается само: после перезагрузки или падения панели вы запускаете её вручную. Для приёмника, за которым вы следите, это приемлемо, но учтите, что тепловая защита процессора работает внутри панели: пока панель не работает, машину ничто не защищает (см. [THERMAL_GUARD.md](THERMAL_GUARD.md)).

### Способ B — юниты systemd (запуск при загрузке, перезапуск после сбоя)

В репозитории есть два готовых юнита, `phantomsdr-admin.service` и `phantomsdr-proxy.service`. Исправьте в обоих `User=` и пути, затем:

```bash
sudo cp phantomsdr-admin.service phantomsdr-proxy.service /etc/systemd/system/
sudo systemctl daemon-reload
./manage_admin.sh stop        # free the ports first
sudo systemctl enable --now phantomsdr-admin
sudo systemctl enable --now phantomsdr-proxy
```

Повседневные команды тогда становятся такими:

```bash
sudo systemctl start   phantomsdr-admin
sudo systemctl stop    phantomsdr-admin
sudo systemctl restart phantomsdr-admin
systemctl status       phantomsdr-admin
sudo journalctl -u phantomsdr-admin -f
```

Те же четыре с `phantomsdr-proxy` или обе сразу: `sudo systemctl restart phantomsdr-admin phantomsdr-proxy`.

`admin.log` и `proxy.log` работают точно так же, как раньше — юниты дописывают в те же файлы.

Одно действие стоит выполнить один раз: установить правило tmpfiles из `tmpfiles/phantomsdr-logs.conf` (сначала исправьте в нём пути и пользователя). systemd создаёт эти два журнала от `root` до перехода на `User=`, и тогда кнопка **Clear Logs** в панели не срабатывает с ошибкой `Permission denied` — см. ниже «Clear Logs сообщает Permission denied». `setup_admin.sh` устанавливает правило за вас.

Юнит панели содержит `SupplementaryGroups=cpufreq`: именно это позволяет этапу throttle тепловой защиты снижать частоту процессора, не запуская панель от root. Сначала создайте эту группу с помощью `./setup-cpufreq-perms.sh`, иначе systemd откажется запускать юнит; удалите строку, если этап throttle вам не нужен.

Возврат к способу A:

```bash
sudo systemctl disable --now phantomsdr-admin
sudo systemctl disable --now phantomsdr-proxy
```

> ⚠️ **Не смешивайте эти два способа.** При включённых юнитах `./manage_admin.sh stop` systemd отменит через пять секунд, а `./manage_admin.sh start` даст вам вторую, неуправляемую копию, которая дерётся за тот же порт с копией systemd. (`restart` убран из скрипта именно поэтому; теперь он выводит ошибку и отсылает к `systemctl`.) `./manage_admin.sh status` только читает, поэтому остаётся полезным в обоих случаях.

### Перезапуск панели

Далее в этом документе в нескольких местах сказано «перезапустите панель». Имеется в виду то, что соответствует вашему способу:

```bash
# Способ B — юниты systemd (обычная установка)
sudo systemctl restart phantomsdr-admin phantomsdr-proxy

# Способ A — юниты не установлены
./manage_admin.sh stop && ./manage_admin.sh start
```

Юнит поставляется с `KillMode=process`, и эта строка принципиальна. Если вы запускаете SDR из панели, приёмник является потомком юнита панели и наследует его cgroup. При стандартном для systemd значении `KillMode=control-group` перезапуск панели снял бы вместе с ней spectrumserver, его сторожевой таймер и демон autorun — предварительно застряв на все 90 секунд тайм-аута остановки. С `KillMode=process` systemd подаёт сигнал только самой панели, поэтому `sudo systemctl restart phantomsdr-admin` оставляет загруженный приёмник в эфире.

**Обновление юнита, установленного до v4.1.0.** В старых файлах юнита этой строки нет, и перезапуск панели её не добавит: `systemctl restart` заново запускает программу, но не меняет её конфигурацию. Правьте *установленную* копию — файл в репозитории лишь шаблон, systemd его никогда не читает:

```bash
sudo nano /etc/systemd/system/phantomsdr-admin.service
```

Добавьте `KillMode=process` в раздел `[Service]`, рядом с `Restart=always`. Затем заставьте systemd перечитать файл и проверьте:

```bash
sudo systemctl daemon-reload
systemctl show phantomsdr-admin -p KillMode
```

Вторая команда должна вывести `KillMode=process`. Если по-прежнему выводится `control-group`, systemd работает с кэшированной копией — `systemctl show phantomsdr-admin -p NeedDaemonReload` показывает `yes`, пока перезагрузка конфигурации не выполнена. Ведущие пробелы в файлах юнитов игнорируются, поэтому отступы значения не имеют.

## Шаг 4 — Откройте порт в межсетевом экране

Откройте в межсетевом экране только **публичный порт прокси**. Выставлять наружу внутренний порт панели администратора не нужно:

## Шаг 5 — Функция отключения пользователей

Страница Users показывает каждого подключённого слушателя. В каждой строке указаны IP пользователя, настроенная частота, режим и длительность подключения. Чтобы отключить пользователя, нажмите в его строке кнопку **⚡ Kick** — разрывается только это TCP-соединение. Все остальные слушатели остаются на связи и ничего не замечают.

Отключение мгновенное и точечное: сервер не перезапускается, звук ни у кого не прерывается, а отключённый пользователь может сразу переподключиться (функция нужна для устранения проблемных или зависших соединений, а не для блокировки).

Внутри отключение использует `ss -K dst <IP> dport <port>`, чтобы закрыть конкретный TCP-сокет. Для этого требуется возможность Linux, которую сценарий настройки предоставляет автоматически. Если вы пропустили настройку или кнопка сообщает об ошибке, задайте её вручную:

```bash
sudo setcap cap_net_admin+ep $(which ss)
# Verify:
getcap $(which ss)    # should show: cap_net_admin=ep
```

## Конфигурация — admin_config.json

Вся конфигурация времени выполнения находится в `admin_config.json` в каталоге PhantomSDR-Plus. `setup_admin.sh` создаёт исходный файл; последующие изменения можно вносить через страницу Settings или правкой файла напрямую.

Ключевые поля, записываемые `setup_admin.sh`:

| Ключ | Описание |
|---|---|
| `port` | Внутренний порт панели администратора (сюда привязывается `admin_server.py`) |
| `public_port` | Порт spectrumserver (используется страницей Users для запроса `/users`) |
| `proxy_port` | Публичный порт, который слушает прокси |
| `sdr_host` | Узел, по которому прокси обращается к spectrumserver — `127.0.0.1` (см. ниже) |
| `password_hash` | Хеш SHA-256 пароля администратора |
| `sdr_base_dir` | Путь к вашей установке PhantomSDR-Plus |
| `sdr_process_name` | Имя отслеживаемого процесса (по умолчанию: `spectrumserver`) |
| `start_script` / `stop_script` | Скрипты, которыми панель запускает и останавливает SDR-сервер, — через них действует и тепловая защита |

Ключи тепловой защиты (все необязательны — панель записывает их при сохранении настроек Thermal Guard, а отсутствующие берут эти значения по умолчанию):

| Ключ | По умолчанию | Описание |
|---|---|---|
| `thermal_enabled` | `true` | Общий выключатель защиты |
| `thermal_mode` | `"log"` | `log` (только запись, никаких действий) · `throttle` · `stop` · `stop+restart` |
| `thermal_warn` | `null` | Температура предупреждения °C; `null` = вывести из критического порога вашего процессора |
| `thermal_throttle` | `null` | Температура, при которой снижается верхний предел частоты; `null` = автоматически |
| `thermal_stop` | `null` | Температура, при которой сервер останавливается; `null` = автоматически |
| `thermal_resume` | `null` | Температура, ниже которой должен опуститься процессор для восстановления; `null` = автоматически |
| `thermal_sustain_s` | `60` | Секунд удержания температуры остановки до действия |
| `thermal_warn_sustain_s` | `30` | Секунд удержания температур предупреждения и throttle |
| `thermal_resume_s` | `300` | Секунд ниже температуры восстановления до снятия блокировки |
| `thermal_max_stops_hour` | `2` | Тепловых остановок в час до отключения автоматического перезапуска |
| `thermal_test_temp` | `null` | Фиктивная температура для проверки; `null` = использовать реальный датчик |

Изменения вступают в силу со следующим замером — через пару секунд, без перезапуска.

Чтобы изменить порты после первоначальной настройки, отредактируйте `admin_config.json` и перезапустите:

```bash
sudo systemctl restart phantomsdr-admin phantomsdr-proxy   # B
./manage_admin.sh stop && ./manage_admin.sh start        # A
```

## Настройка `sdr_host`

`proxy.py` подключается к `spectrumserver` по петлевому адресу — `sdr_host` равен `127.0.0.1` в `admin_config.json`, его записывает туда `setup_admin.sh`. Менять это обычно не требуется.

Указывайте реальный адрес только в том случае, если `spectrumserver` работает на **другой машине**, чем прокси. После этого выполните [Перезапуск панели](#перезапуск-панели).

> **Что изменилось:** прежние версии требовали, чтобы `sdr_host` был локальным IP машины, потому что `spectrumserver` закрывал WebSocket-соединения, приходящие с петлевого адреса. Этот фильтр убран, поэтому локальные соединения работают нормально. Два следствия: открытие `http://localhost:<port>` на самой машине сервера теперь показывает полный интерфейс (раньше страница загружалась, но оставалась пустой), и прокси больше не ломается, когда DHCP выдаёт машине новый IP. Если вы обновляетесь и в вашем `admin_config.json` всё ещё стоит локальный IP, замените его на `127.0.0.1` или запустите `setup_admin.sh` заново.

## proxy.py — что это и когда нужно

`proxy.py` размещает и сервер SDR, и панель администратора на **одном публичном порту**, маршрутизируя по префиксу пути:

| Путь | Направляется в |
|---|---|
| `/admin*` | Панель администратора (`localhost:<port>`) |
| Всё остальное | Spectrumserver (`<sdr_host>:<public_port>`) |

Без прокси вам пришлось бы открывать два порта отдельно. С ним вы открываете только один.

Прокси также снимает ограничение размера сообщения WebSocket в 4 МБ (важно для больших кадров FFT с RX-888 при 60 MSPS), передаёт настоящие IP клиентов через заголовки `X-Forwarded-*` и поддерживает долгоживущие соединения через NAT с помощью 30-секундного heartbeat.

## Файлы журналов

| Файл | Содержимое |
|---|---|
| `admin.log` | Вывод панели администратора |
| `proxy.log` | Стартовый баннер прокси + по одной строке доступа на каждый проксированный запрос |
| `logwebsdr.txt` | Журнал скрипта запуска и сторожа — старт/остановка, драйвер приёмника, регистрация на websdr.org |
| `spectrumserver.log` | Вывод самого процесса приёмника — настройка FFT и OpenCL, подключения клиентов, ошибки. Самый крупный из этих файлов; он ротируется, поэтому рядом может лежать `spectrumserver.log.1` |
| `rade.log` | Журнал sidecar-процесса RADE/FreeDV |
| `autorun.log` | Журнал демона декодера — споты, SNR, дрейф |
| `crash.log` | Отчёты о сбоях и тепловые события: трассировки `[CRASH]` / `[TERMINATE]`, заметки `[EXIT]` и строки `[THERMAL]` от защиты. **Обычно пуст** — всё, что в нём есть, стоит прочитать |

Всё это доступно для чтения на вкладках **Log Viewer** панели (LOGWEBSDR, SPECTRUMSERVER, ADMIN, RADE, CRASH, AUTORUN, PROXY). Просмотрщик показывает последние 150 строк выбранной вкладки и обновляется каждые 3 секунды при включённом автообновлении; он читает только конец файла, поэтому его размер не важен.

### Ротация proxy.log и admin.log

`proxy.log` записывает каждый проксированный запрос, а `admin.log` — каждый запрос, который доходит до самой панели. По умолчанию не ротируется ни один из них. Раньше опросы панели преобладали в обоих файлах — `/admin/api/status` выполняется каждые ~3 секунды, пока открыта вкладка, — но теперь эти опросы отфильтровываются из обоих журналов (см. ниже), поэтому ротация ограничивает медленный рост, а не поток.

В репозитории есть конфигурация logrotate в `logrotate/phantomsdr` (ежедневно или раньше, если журнал превысит 10 МБ; хранит 7 сжатых архивов в `logproxy/`, чтобы они не засоряли корень проекта). **Она зависит от площадки — откройте её и измените три пути к журналам, путь `olddir` и пользователя `su` под свою машину перед установкой**, затем:

```bash
sudo cp logrotate/phantomsdr /etc/logrotate.d/phantomsdr
sudo logrotate -d /etc/logrotate.d/phantomsdr     # dry run, should list all three logs
```

`logrotate/phantomsdr` в репозитории и `/etc/logrotate.d/phantomsdr` — две **независимые копии**; `cp` их не связывает. Правка файла в репозитории ничего не меняет на работающей системе, пока вы снова не выполните `sudo cp` выше. Logrotate читает только копию в `/etc`.

Конфигурация использует `copytruncate`, и это обязательно: `manage_admin.sh` запускает оба процесса с `>> <log>`, и ни один не переоткрывает свой стандартный вывод, поэтому ротация через переименование оставила бы их писать в перемещённый файл, а новый журнал навсегда остался бы пустым.

Архивы попадают в `logproxy/` (создаётся автоматически благодаря `createolddir`) и называются `proxy.log.1.gz` … `proxy.log.7.gz`, самый свежий первым. Прочитать один можно командой `zcat logproxy/proxy.log.1.gz | less`, а искать сразу во всех — `zgrep "pattern" logproxy/*.gz`.

Кнопка **Clear Logs** панели очищает **все** файлы из таблицы выше, включая `autorun.log` и `proxy.log` (`CLEAR_EXCLUDE` в `admin_server.py` пуст). Учтите, чего это стоит в случае `autorun.log`: его история декодирования — единственная запись о том, что и когда было принято, и восстановить её невозможно; после очистки остаётся лишь то, что logrotate уже перенёс в `logproxy/`, то есть теряется всё декодированное с момента последней ротации. Очищать его при работающем декодере безопасно: демон держит файл открытым с `O_APPEND` и продолжает писать в тот же inode. Всплывающее сообщение называет, что очищено, а если файл не удалось записать — например, `proxy.log`, принадлежащий другому пользователю при раздельных учётных записях, — оно называет этот файл и ошибку вместо сообщения об успехе и оставляет панель этого журнала на экране, а не очищает её. Файлы обнуляются на месте и никогда не удаляются: и `manage_admin.sh`, и юниты systemd открывают их с `O_APPEND`, поэтому удалённый файл продолжал бы наполнять невидимый inode до перезапуска службы.

Успешные опросы отфильтровываются из **обоих** журналов доступа — фильтром `QuietPollFilter` в `proxy.py` и таким же в `admin_server.py`. Панель обращается к `/admin/api/status` каждые 3 секунды, а к `/admin/api/logs`, `/admin/api/autorun/status`, `/admin/api/users`, `/admin/api/graph-stats` и `/admin/api/chat` — каждые 5 секунд; без фильтрации это ~95 % обоих файлов. Отбрасываются только обычные `200` по этим путям: любой другой статус, путь или метод записывается как прежде, поэтому неудачный опрос остаётся виден, а изменяющие состояние действия (`kick`, `autorun/start`, …) идут по отдельным путям и записываются всегда. Единственное намеренное исключение — `/admin/api/logs/clear`, отфильтрованный в обоих файлах: его собственная строка доступа пишется *после* очистки, поэтому без фильтра каждая успешная очистка оставляла одну свежую строку в только что очищенном журнале, и кнопка выглядела неработающей.

Поскольку `proxy.log` — журнал доступа, он содержит IP-адреса посетителей и строки user-agent; учитывайте это, прежде чем делиться им при обращении за помощью.

### «Clear Logs» сообщает Permission denied

На машине, где юниты systemd были установлены на чистое дерево, кнопка может вернуть:

```
✗ Could not clear admin.log ([Errno 13] Permission denied: /home/you/PhantomSDR-Plus/admin.log),
  proxy.log ([Errno 13] Permission denied: /home/you/PhantomSDR-Plus/proxy.log)
```

Это всегда те же два файла и никогда остальные пять, потому что только их создаёт сам systemd. `StandardOutput=append:` открывается из PID 1 **до** перехода на `User=`, поэтому ещё не существующий журнал создаётся как `root:root 0644`. Панель работает от вашего пользователя и не может его очистить. Остальные пять журналов создают сценарии запуска, которые и так работают от вашего пользователя, поэтому они очищаются нормально. Там, где эти два файла появились раньше юнитов — их создал `manage_admin.sh` через `>>` — владелец уже правильный и кнопка работает; именно поэтому проблема проявляется только на свежей установке, сразу начатой с systemd.

Проверьте командой `ls -l admin.log proxy.log`: у сбойных будет `root root`. Исправьте их:

```bash
sudo chown "$(id -un):$(id -gn)" admin.log proxy.log
sudo chmod 664 admin.log proxy.log
```

Перезапуск не нужен — systemd продолжает писать через уже открытый файловый дескриптор, а дозапись не меняет владельца. Нажмите **Clear Logs** ещё раз, и оба файла очистятся.

**Не удаляйте файлы вместо этого.** Оба открыты с `O_APPEND`; удаление оставит systemd заполнять невидимый inode до перезапуска службы, а вновь появившийся файл снова будет принадлежать root.

Чтобы это не повторялось, установите правило tmpfiles, которое поставляется в репозитории: `tmpfiles/phantomsdr-logs.conf`. Оно заново создаёт оба журнала с правильным владельцем при каждой загрузке, до запуска юнитов, так что удалённый журнал — ручная уборка, переустановка, перенесённый каталог установки — никогда не вернётся принадлежащим root. **Правило зависит от машины: откройте его и сначала замените два пути и user:group на свои**, затем:

```bash
sudo cp tmpfiles/phantomsdr-logs.conf /etc/tmpfiles.d/99-phantomsdr-logs.conf
sudo systemd-tmpfiles --create /etc/tmpfiles.d/99-phantomsdr-logs.conf
```

Как и с `logrotate/phantomsdr`, файл в репозитории и копия в `/etc` независимы — правка репозиторной копии ничего не меняет, пока вы не выполните `cp` заново. В systemd 254 и новее правило также исправляет владельца и права уже существующего журнала, то есть устраняет и текущий сбой; в более старых версиях кнопку разблокирует именно `chown` выше.

`setup_admin.sh` делает всё это за вас при установке юнитов, поэтому установка через сценарий с этим не сталкивается. Шаги выше — для пары, установленной вручную, или для установки, сделанной раньше, чем в сценарии появился шаг с владельцем журналов.

Logrotate не возвращает проблему: поставляемая конфигурация использует `copytruncate`, который сохраняет тот же inode и, следовательно, того же владельца.

## Удаление сообщений чата

Страница Chat History перечисляет каждое сообщение текущего журнала чата. У каждой записи есть кнопка **🗑 Delete**, которая немедленно убирает именно это сообщение из журнала — без перезапуска сервера.

Как это работает:

- Панель администратора переписывает файл журнала чата на месте, удаляя только строку выбранного сообщения.
- Изменение вступает в силу для любого пользователя, который перезагрузит чат; уже загруженная история в открытых вкладках задним числом не обновляется.
- Очистка всего журнала (кнопка **Clear All**) обнуляет файл, что также действует без перезапуска.

Кнопка удаления одинаково отображается во всех пяти вариантах приложения Svelte. Если удаление, похоже, не срабатывает, убедитесь, что у панели администратора есть право записи в файл журнала чата:

```bash
ls -l ~/PhantomSDR-Plus/chat.jsonl   # path depends on your config
```

## Трансляция сообщений на водопад

Панель **Waterfall Message** позволяет вывести постоянный текстовый баннер на водопад каждого подключённого пользователя, не трогая процесс сервера.

### Отправка сообщения

1. Откройте панель администратора и перейдите в **Waterfall Message**.
2. Введите текст сообщения и выберите цвет (шестнадцатеричный, например `#ffdd00`).
3. Нажмите **Send** — сообщение сразу появится во всех активных видах водопада.

### Очистка сообщения

Нажмите **Clear**, чтобы убрать баннер со всех водопадов. Состояние сообщения хранится в памяти панели администратора; оно очищается автоматически при перезапуске процесса панели.

### Как это работает

Панель администратора предоставляет две внутренние конечные точки, которые пересылает прокси:

| Конечная точка | Метод | Назначение |
|---|---|---|
| `/admin/api/waterfall-message` | `POST` | Задать или очистить текст и цвет текущего баннера |
| `/admin/api/waterfall-message` | `GET` | Вернуть текущее состояние сообщения в виде JSON |

Веб-интерфейс опрашивает состояние сообщения и отрисовывает его наложением на холст водопада. На стороне клиента не требуется ни переподключение WebSocket, ни перезагрузка страницы.

### Типичные применения

- Объявление о плановом обслуживании: `"Server restart in 10 minutes"`
- Сообщение об условиях прохождения: `"Solar flux 180 — 10m wide open"`
- Приветствие: `"Welcome to SV1BTL WebSDR — Athens, KM17"`

## Системные графики

Страница **Графики** отображает четыре величины на общей оси времени:

- **Частота ЦП** — средняя частота по всем ядрам, в ГГц
- **Загрузка ЦП** — общая загрузка, в процентах
- **Температура ЦП** — в °C, с пунктирными отметками на 70 °C (тепло) и 80 °C (критично)
- **Пользователи онлайн** — слушатели, подключённые к WebSDR в этот момент

Диапазон выбирается кнопками **15 MIN / 1 HOUR / 4 HOURS / 12 HOURS / 24 HOURS**. При наведении на график появляется перекрестие со всеми четырьмя значениями на этот момент. Четыре карточки над графиком всегда показывают самый свежий отсчёт.

### Как работает выборка

Фоновый поток в `admin_server.py` берёт один отсчёт каждые **2 секунды**. Отсчёты хранятся в двух уровнях: последний **час** в полном разрешении 2 секунды (1800 точек) и **24 часа** тридцатисекундных средних (2880 точек) для длинных диапазонов. Страница выбирает уровень, покрывающий выбранный диапазон, и пишет `30s averages` в заголовке, когда показывает усреднённый уровень.

Целые сутки с разрешением 2 секунды — это ~43000 точек: десятки МБ памяти, первая передача в несколько мегабайт и около 40 точек на пиксель, чего не может отобразить ни один экран. Усреднение до 30 секунд умещает сутки в 2880 точек.

Выборка запускается вместе с панелью администратора, а не при первом открытии страницы, поэтому страница открывается на уже накопленной истории.

Буфер находится **только в памяти**: на диск ничего не пишется, а история теряется при перезапуске панели. Это сделано намеренно — так функция остаётся вне ротации журналов и не занимает диск.

2 секунды дают почти живую картину и достаточно коротки, чтобы не искажать частоту ЦП, которая на современном процессоре от отсчёта к отсчёту прыгает между частотой простоя и турбо. Один отсчёт стоит около миллисекунды, поэтому выборка ничтожна на фоне SDR-сервера. Страница опрашивает в ритме своего уровня — каждые 2 секунды на живых диапазонах и каждые 30 секунд на усреднённых, поскольку более частые запросы возвращают лишь пустые ответы.

Чтобы изменить период или глубину хранения, отредактируйте эти константы в начале блока выборки в `admin_server.py` и перезапустите:

```python
GRAPH_INTERVAL_S   = 2          # секунд между точными отсчётами
GRAPH_FINE_S       = 3600       # глубина точного уровня (1 ч)
GRAPH_COARSE_EVERY = 15         # точных отсчётов на укрупнённую точку (15 x 2 с = 30 с)
GRAPH_COARSE_S     = 24 * 3600  # глубина укрупнённого уровня (24 ч)
```

### Откуда берутся значения

| Величина | Источник |
|---|---|
| Частота ЦП | `psutil.cpu_freq()`, иначе `/sys/devices/system/cpu/cpu*/cpufreq/`. Это те же данные ядра, которые форматирует `cpufreq-info`, поэтому **cpufrequtils не требуется**. |
| Загрузка ЦП | `psutil.cpu_percent()` |
| Температура ЦП | `psutil.sensors_temperatures()`, иначе `/sys/class/thermal`, затем команда `sensors` |
| Пользователи онлайн | Собственная конечная точка `/users` у spectrumserver — достоверный список сессий. Подсчёт сокетов через `ss` не видит реальные IP клиентов за proxy.py. |

Если величина недоступна на вашей машине, соответствующая панель сообщает об этом, а не рисует нулевую линию. Неудавшееся измерение разрывает линию, чтобы пропуск никогда не выглядел как измеренное значение.

### Почему четыре панели, а не один график

ГГц, проценты, градусы и число людей не имеют общей шкалы. Для одного графика понадобилось бы несколько осей Y, а возникающие при этом пересечения — артефакт масштабирования, а не факт о сервере. Четыре панели на одной оси времени сохраняют сравнение честным. Каждая панель начинается с нуля, поэтому высота кривой остаётся пропорциональной значению.

Цвет зарезервирован за температурой, где янтарный и красный отмечают указанные пороги. Остальные панели используют один цвет, поскольку каждая содержит один ряд, который уже назван её заголовком.

### Конечная точка

`GET /admin/api/graph-stats?since=<epoch>` (требуется вход) возвращает отсчёты новее `since`, поэтому страница опрашивает инкрементально, а не скачивает весь буфер на каждом цикле.

## Thermal Guard

> 📖 **Полное руководство: [THERMAL_GUARD.md](THERMAL_GUARD.md)** — четыре режима и что должен сделать сисоп в каждом, работа без панели, этап throttle без root, проверка и устранение неполадок.

Останавливает SDR-сервер, когда процессор становится опасно горячим, и запускает его снова, когда тот остынет. Она входит в состав панели — устанавливать ничего не нужно — и появляется карточкой **THERMAL GUARD** на Панели управления, а её настройки находятся в разделе **Настройки**.

Поставляется **бездействующей**: режим начинается с `log`, поэтому изначально она лишь записывает, что *сделала бы*. Ничто не трогает ваш сервер, пока вы не смените режим.

### Работает с любым способом запуска и остановки

Защита никогда не пытается выяснить, что присматривает за вашим сервером. Она действует через скрипты, заданные как **Default start script** и **Default stop script** в Настройках, и пока процессор перегрет, повторяет остановку при **каждой проверке** (каждые 2 с). Всё, что возвращает сервер к жизни — watchdog внутри `start-*.sh`, юнит systemd, задание cron, сеанс `tmux` — отменяется за пару секунд, пока машина не остынет. Это и есть *блокировка* (lockout).

Если скрипт остановки не задан, она посылает `SIGTERM` процессу, названному в `sdr_process_name`, а через 10 секунд отсрочки — `SIGKILL`.

### Пороги берутся из вашего собственного процессора

Вместо фиксированного числа, которое было бы неверным на большинстве машин, защита читает критический порог, публикуемый ядром для вашего процессора, и отсчитывает от него назад:

| Ваш процессор сообщает | предупреждение | throttle | остановка | восстановление |
|---|---|---|---|---|
| Intel, предел 100 °C | 88 | 92 | **95** | 75 |
| AMD Ryzen, предел 95 °C | 83 | 87 | **90** | 70 |
| Raspberry Pi, предел 85 °C | 73 | 77 | **80** | 60 |

Это важно: фиксированные 95 °C почти нормальны для Intel, но на Ryzen — где Tctl по замыслу держится на 95 °C под бустом — они остановили бы сервер на совершенно здоровой машине, а на Pi, который снижает частоту уже при 80 °C, не сработали бы никогда. Любой порог можно задать вручную в Настройках; оставьте поле пустым для *автоматического* значения.

Чтобы увидеть, каким защита видит ваш компьютер:

```bash
python3 thermal_guard.py --once
```

```
sensor     : hwmon:coretemp
temperature: 58.0 C
crit       : 100.0 C
mode       : log
thresholds : warn 88.0  throttle 92.0  stop 95.0  resume 75.0 (C)
cpufreq    : not writable — throttle stage disabled
```

### Четыре ступени

Остановка сервера — крайняя мера, а не единственный инструмент:

1. **warn** — записывается в журнал, и только.
2. **throttle** — снижает верхний предел частоты процессора на 20 %. Требует драйвер cpufreq *и* право записи в `scaling_max_freq`, то есть обычно root; там, где этого нет (обычный случай для панели без привилегий и для большинства VPS), ступень **отключает себя сама**, и защита переходит от warn сразу к stop. `./setup-cpufreq-perms.sh` даёт это право записи группе `cpufreq`, так что ступень работает без root — см. [THERMAL_GUARD.md](THERMAL_GUARD.md#8-включение-этапа-throttle-без-root).
3. **stop** — выполняет ваш скрипт остановки и удерживает сервер выключенным (см. блокировку).
4. **resume** — после того как процессор `thermal_resume_s` (по умолчанию 5 минут) держится ниже температуры восстановления, предел частоты возвращается, а в режиме `stop+restart` снова выполняется ваш скрипт запуска.

Каждая ступень должна **удерживаться** своё время — 30 с для warn и throttle, 60 с для stop — так что короткий всплеск во время компиляции никогда её не запустит.

Повторные срабатывания ограничены параметром `thermal_max_stops_hour` (по умолчанию 2). По достижении предела *автоматический перезапуск* отключается, а защита продолжает работать, чтобы перегревающаяся машина не металась между работой и остановкой.

### Какие датчики используются

Только настоящие датчики на кристалле процессора: `coretemp` (Intel), `k10temp` / `zenpower` (AMD), `cpu_thermal` / `soc_thermal` (ARM, Raspberry Pi). Берётся самое высокое показание чипа, а не среднее.

`acpitz` и безымянные тепловые зоны **намеренно игнорируются** — они часто сообщают температуру корпуса или платы на десятки градусов ниже реальной температуры процессора, поэтому защита, доверяющая им, не сработала бы тогда, когда это важно. Если на вашей машине нет пригодного датчика (обычное дело на VPS или внутри контейнера), карточка прямо сообщает об этом (`no trusted CPU sensor`), и защита остаётся неактивной, а не делает вид, что защищает вас.

### Что она записывает

Всё попадает в `crash.log`, то есть во вкладку **CRASH** просмотрщика журналов, по одному событию на строку:

```
[THERMAL] warn: 89.0C (warn=88.0 crit=100.0) sustained 31s
[THERMAL] throttle: 93.0C sustained 30s — cpufreq max lowered 20%
[THERMAL] STOPPED server: 96.0C sustained 62s (stop=95.0 crit=100.0) — Started stop-websdr.sh
[THERMAL] lockout: process reappeared at 94.0C — re-stopped [3 time(s) so far]
[THERMAL] recovered: 74.0C held below 75.0 — lockout cleared
[THERMAL] auto-restart: Started start-rx888mk2.sh
```

Строка блокировки записывается не чаще раза в минуту, чтобы упорно сопротивляющийся надзиратель не затопил журнал.

### Проверьте, прежде чем доверять

Задайте **TEST TEMPERATURE** в Настройках выше вашего порога остановки. Защита воспримет это как настоящее показание, и весь путь — warn, throttle, stop, блокировка, восстановление, перезапуск — пройдёт по вашему желанию. Очистите поле, чтобы вернуться к реальному датчику.

> Если провести эту проверку в режиме `stop`, сервер действительно остановится и ваши слушатели будут отключены. Делайте это, когда никого нет, или оставьте режим `log`, где проверка показывает, что *произошло бы*, ничего не трогая.

### Как её лучше внедрить

1. Оставьте режим **`log`** на неделю и работайте как обычно.
2. Читайте вкладку CRASH после тяжёлых моментов — полной пересборки, жаркого дня. Если там ничего нет, ваша машина даже близко не подходила.
3. Если записанные температуры выглядят правильно, переключите режим на **`stop`** (или **`stop+restart`**, чтобы сервер возвращался сам).
4. Подтвердите работу один раз полем тестовой температуры и оставьте её в покое.

### Снятие блокировки

Кнопка **CLEAR LOCKOUT** на карточке Панели управления снимает блокировку и ограничение частоты срабатываний. Она не разоружает защиту: если процессор всё ещё слишком горяч, следующая проверка просто снова остановит сервер. Пользуйтесь ею после того, как исправили охлаждение.

### Endpoint

`GET /admin/api/thermal` (требуется вход) возвращает полное состояние защиты — датчик, пороги, ступень, блокировку, последнее событие. `POST` с `{"action":"reset"}` делает то же, что и кнопка CLEAR LOCKOUT.

### Без панели администратора

`thermal_guard.py` использует только стандартную библиотеку и работает самостоятельно, читая тот же `admin_config.json`:

```bash
python3 thermal_guard.py --once              # вывод датчика, критического порога и порогов
python3 thermal_guard.py                     # запуск как службы (только запись, пока не взведена)
python3 thermal_guard.py --mode stop+restart # взвести без единого файла конфигурации
python3 thermal_guard.py --config /path/to/other.json
python3 thermal_guard.py --help
```

`--mode` имеет приоритет над `thermal_mode` из файла конфигурации, так что машину без панели можно взвести прямо из её systemd-юнита, вообще без JSON.

## Spot Reporting (autorun FT8/FT4/JS8/WSPR)

Вкладка **Spot Reporting** управляет службой autorun (`autorun/index.js`) — процессом Node.js, который декодирует FT8/FT4/JS8/WSPR на стороне сервера прямо с приёмника и выгружает споты в сети отчётности:

- **FT8 / FT4 / JS8 → PSK Reporter** (IPFIX/UDP)
- **WSPR → wsprnet.org** (HTTP)

> **JS8 сообщается только на скорости Normal** — 15-секундном вызывном цикле, где идут heartbeat и CQ. Споты берутся из heartbeat, compound-кадров и направленных сообщений; групповые адресаты вроде `@ALLCALL` и позывные, которые декодер не смог распознать (`<....>`), не сообщаются никогда. JS8 использует ту же очередь PSK Reporter, что FT8 и FT4, и считается отдельно, точно так же, как они.


**Отчётность по умолчанию ВЫКЛЮЧЕНА.** Ничего не выгружается, пока вы не включите приёмник отчётов и не нажмёте **Start**. Декодирование и выгрузка независимы: служба может декодировать и вести журнал при выключенной отчётности, так что вы можете проверить активность, прежде чем что-либо станет публичным.

> ⚠️ Споты выгружаются в публичные сети под **вашим позывным**. Включайте только диапазоны и режимы, которые ваш приёмник действительно слышит, и указывайте правильный локатор.

### Предварительные требования

Службе autorun нужны Node.js 22+, пакеты npm `ws` + `cbor-x` (разрешаются через символическую ссылку `autorun/node_modules` → `frontend/node_modules`) и `util-linux` (`taskset`). Установщики настраивают всё это автоматически — см. [раздел Autorun Spot Reporter в INSTALLATION.md](INSTALLATION.md#autorun-spot-reporter-ft8ft4wspr). Если **Start** не срабатывает, обычная причина — эта ссылка или `taskset` (см. «Устранение неполадок» ниже).

### Работа с вкладкой

1. **Идентификация** — позывной и локатор. Предзаполняются из `frontend/site_information.json` (`siteSysop` / `siteGridSquare`, усечены до 6 символов); при необходимости переопределите здесь.
2. **Матрица диапазон × режим** — отметьте комбинации для декодирования. Строки — диапазоны, столбцы — FT8 / FT4 / JS8 / WSPR; неподдерживаемые ячейки отключены. WSPR дополнительно охватывает диапазоны НЧ/СЧ (2200 м, 630 м) и дополнительный европейский канал 80 м.
3. **Приёмники отчётов** — включите **PSK Reporter** и/или **wsprnet** (оба по умолчанию выключены).
4. **Max slots** — предохранительное ограничение на число одновременно работающих слотов диапазон/режим.
5. **Start / Stop** — запускает/завершает службу (привязанную к старшим ядрам ЦП через `taskset`, выбираемым автоматически для машины — см. *Требования к ресурсам и ограничения* ниже). **Save** / **Reload** сохраняют и перечитывают конфигурацию; **Free All** очищает все слоты.

Карточка состояния обновляется каждые 5 с и показывает состояние работы, счётчики декодирования/выгрузки и время последней отправки. Значок **📶 REPORTING** появляется на главном водопаде, пока отчётность активна.

> **«0 sent» в первые минуты — это нормально.** PSK Reporter выгружает пакетами каждые **5 минут**, а wsprnet — каждые **2 минуты**; споты ждут очередной отправки. Карточка состояния показывает число ожидающих и периодичность.

### Смена диапазонов или режимов во время работы

**Изменения не вступят в силу до перезапуска демона.** `autorun/index.js` читает `autorun.json` ровно один раз, при запуске. Ни слежения за файлом, ни сигнала перезагрузки нет — обрабатываются только SIGINT и SIGTERM, оба означают завершение. Поэтому работающий демон продолжает декодировать те слоты, с которыми был запущен, что бы вы ни сохранили после.

Чтобы применить изменение:

1. Отметьте / снимите отметки с диапазонов и режимов
2. **SAVE CONFIG**
3. **STOP**
4. **START**

Или проще: **STOP** → изменить флажки → **START**, поскольку START сохраняет конфигурацию перед запуском.

> ⚠️ **Нажатие START без предварительного STOP изменение не применяет.** START сохраняет конфигурацию, затем запрос на запуск отвечает `already running`, и ничего не перезапускается. Вы увидите сообщение «сохранено» рядом с ошибкой «already running», пока демон продолжает работать со **старыми** диапазонами — это легко принять за успех. Всегда сначала STOP.

Что перезапуск делает со счётчиками:

- **Итоги рядом с каждым флажком сохраняются** — они в `autorun-totals.json`, который при завершении не удаляется.
- **Плитки по декодерам обнуляются**, они считаются за один запуск.
- **Ничего из очереди не теряется**: при завершении ожидающие споты отправляются.
- **Только что включённый** диапазон начинает с `0`; диапазон, использовавшийся **ранее**, продолжает прежний итог.
- Диапазон, с которого вы **сняли отметку, сохраняет своё число** рядом с теперь пустым флажком; история не удаляется.

Декодирование прерывается лишь на несколько секунд между STOP и START.

### Счётчики спотов

Показаны два разных счёта, отвечающие на разные вопросы.

**SPOTS UPLOADED PER DECODER** — плитка на каждый декодер (FT8 / FT4 / JS8 / WSPR) со спотами, выгруженными **с последнего запуска демона**, а под ней число декодирований и сколько ещё в очереди. Stop/Start обнуляет их. Декодер, у которого назначение выключено, показывает свои декодирования и `reporting off` вместо голого `0`, потому что ноль выгрузок здесь — настройка, а не сбой.

**Число рядом с каждым флажком** в BANDS & MODES — это спотов выгружено **за всё время** для этой комбинации диапазона и режима. Они хранятся в `autorun-totals.json` и переживают перезапуски. **Янтарный цвет с точкой впереди** (`·123`) означает, что слот декодировал, но пока ничего не выгрузил. Между отправками это нормально — PSK Reporter выгружает каждые 5 минут, wsprnet каждые 2 — поэтому счётчики FT8/FT4 первые минуты после запуска стоят янтарными. Янтарным он остаётся и если назначение этого декодера выключено. Простой `0` без точки означает, что слот включён, но пока ничего не декодировал: WSPR стоит на нуле несколько минут после запуска, поскольку работает в двухминутном цикле, тогда как FT8 уже считает сотнями. Слот, который демон никогда не запускал, не показывает ничего. При наведении видны выгрузки, декодирования и время последней выгрузки.

FT8 и FT4 используют одну очередь отправки в PSK Reporter, поэтому демон относит каждый спот к своему режиму и диапазону в момент отправки; разбивка не оценивается задним числом из итогов.

**Обнуление счётчиков.** **FREE ALL SLOTS** снимает отметки со всех диапазонов и режимов, выключает оба назначения, останавливает демон и **стирает итоговые счётчики** — после этого рядом с флажками не показывается ни одного числа. Это единственный способ их обнулить, и отменить его нельзя. Кнопка останавливает демон и ждёт его завершения, прежде чем удалить `autorun-totals.json`, поскольку демон перезаписывает этот файл при завершении; удаление при работающем демоне просто вернуло бы числа.

### Требования к ресурсам и ограничения

Служба намеренно нетребовательна и работает на слабом оборудовании (четырёхъядерного i5 достаточно), но есть реальные ограничения, о которых стоит знать.

**Привязка autorun к ядрам учитывает конфигурацию и выполняется автоматически.** **Служба autorun** всегда запускается панелью администратора (`admin_server.py`), поэтому её привязка задаётся при любой установке без настройки: из числа процессоров выводится диапазон ядер для `taskset`, резервирующий несколько старших ядер под декодирование, либо на ≤ 4 ядрах служба работает без привязки.

**Привязка spectrumserver зависит от вашего способа запуска.** То, как вы запускаете spectrumserver, различается от установки к установке (тип SDR, инструменты, личные сценарии), поэтому этот документ не предполагает какого-либо конкретного лаунчера. Панель администратора не запускает и не привязывает spectrumserver — это целиком зависит от команды или службы, которой вы его запускаете. Если вы хотите держать spectrumserver вне ядер, используемых службой autorun, привяжите его сами через `taskset` в своей команде запуска (см. раздел о переопределении ниже). Если нет, он просто работает без привязки, а планировщик ОС балансирует нагрузку — это верно и безопасно, вы лишь теряете намеренное разделение ядер.

Для справки, служба autorun резервирует эти старшие ядра (поэтому, если вы привязываете spectrumserver, оставьте его на младших ядрах во избежание пересечения):

| Логических ЦП | Использует служба autorun | Оставить для spectrumserver |
|---|---|---|
| ≤ 4 | *без привязки* | *без привязки* |
| 6 | `5` | `0-4` |
| 8 | `6-7` | `0-5` |
| 12 (например, гибрид 8P+4E) | `8-11` | `0-7` |
| 16 | `12-15` | `0-11` |

На машине с **4 ядрами (или меньше)** разделять нечего, поэтому служба autorun тоже работает *без привязки* и делит все ядра — это верно и безопасно, но FFT приёмника и всплески декодирования конкурируют за одни и те же ядра.

**Известные ограничения:**

1. **Настоящее узкое место — spectrumserver и полоса SDR, а не служба.** RX888 на 30 МГц требует OpenCL/GPU; процессор с малым числом ядер без подходящей видеокарты не потянет такой FFT. Сочетайте слабое оборудование с более узкополосным SDR (RSP1A ≈ 10 МГц, RTL-SDR ≈ 2.4 МГц).
2. **WSPR — главный потребитель ЦП.** Его декодер Фано — порт на JS (~30 с на диапазон, однопоточный). Пул из 4 воркеров выполняет 4 декодирования параллельно; включение **более ~4 диапазонов WSPR** одновременно может вывести очередь за пределы 120-секундного интервала, особенно когда SDR конкурирует за ядра. Декодирование FT8/FT4 по сравнению с этим дёшево.
3. **Масштабирование числа слотов.** Оценка ~2–2,5 ядра / 600–700 МБ относится к полным ~28 слотам на восьмиядерной машине. На 4 общих ядрах ограничьтесь несколькими диапазонами (ориентир: ≤ 6 FT8/FT4 + ≤ 3 WSPR) и следите за показателем `queued` пула.
4. **Привязка предполагает гибридную топологию Intel** (младшие ядра — более быстрые P-ядра). На AMD или процессорах с чередующейся нумерацией SMT автоматическое разделение остаётся корректным (без пересечений и сбоев), но утверждение «младшие ядра быстрее» может не выполняться буквально; на процессоре 4C/8T с hyperthreading старшие ядра — это SMT-близнецы, то есть ограничение есть, но полной изоляции нет. Там, где автоматический диапазон неидеален, используйте **ручное переопределение** ниже.
5. **Покрытие диапазонов ограничено приёмником.** Конфигурация RX888 (`sps=60000000` → Найквист 30 МГц) не достаёт до 6 м и выше; таблица диапазонов — от 160 м до 10 м. Другие SDR покрывают то, что позволяет их окно настройки.
6. **Периодичность отчётности.** PSK Reporter отправляет каждые 5 мин, wsprnet — каждые 2 мин; «0 sent» в первые минуты нормально, это не неисправность.

### Ручное переопределение привязки к ядрам (для опытных)

Автоматически выводимое разделение ядер подходит большинству машин, но там, где это не так (AMD CCX/CCD, ARM big.LITTLE, чередующийся SMT), можно задать привязку явно. Два независимых переопределения, каждое принимает список ядер в формате `taskset -c` (`2-3`, `0,2,4`, `0-2,5`) либо `none`/`off`/`unpinned` для отключения привязки. Некорректное значение игнорируется и применяется автоматический вывод — опечатка никогда не помешает запуску.

**Служба autorun** — переменная окружения `AUTORUN_CORES` или поле `"cores"` в `autorun.json` (окружение приоритетнее). Поле `"cores"` сохраняется при **Save** в панели администратора, поэтому ручная правка не теряется. Два способа задать его:

*Вариант A — `autorun.json` (постоянный, рекомендуемый).* Добавьте строку `"cores"` в конфигурацию в корне репозитория, затем выполните **Stop → Start** на вкладке Spot Reporting:

```jsonc
// autorun.json
{ "identity": { "callsign": "SV1BTL", "grid": "KM17VX" },
  "reporting": { "pskreporter": true, "wsprnet": false },
  "slots": [ /* … */ ],
  "cores": "2-3" }          // or "none" to run unpinned
```

*Вариант B — переменная окружения (разово).* Службу запускает панель администратора, поэтому переменная должна быть в окружении **панели** — задайте её и перезапустите панель (окружение приоритетнее значения в `autorun.json`):

```bash
# Способ A — переменная должна быть у запускающего процесса:
./manage_admin.sh stop && AUTORUN_CORES=2-3 ./manage_admin.sh start

# Способ B — systemd игнорирует переменную, заданную в командной строке
# systemctl, поэтому пропишите её в юните:
sudo systemctl set-environment AUTORUN_CORES=2-3
sudo systemctl restart phantomsdr-admin
```

**spectrumserver** — привяжите его сами, добавив `taskset -c <ядра>` перед той командой, которой вы запускаете сервер. Это работает при любом способе запуска (прямой вызов, конвейер SDR, юнит службы и т. п.):

```bash
# pin the server to cores 0-3, direct launch:
taskset -c 0-3 ./build/spectrumserver --config <your-config>.toml < <your-input>
# or in an SDR pipeline:
<your-sdr-source> | taskset -c 0-3 ./build/spectrumserver --config <your-config>.toml
```

> ⚠️ **Сделайте так, чтобы это пережило перезапуски.** Встроенный `taskset` действует только для одного конкретного запуска. Если что-то перезапускает сервер автоматически (сторожевой процесс, служба systemd, запись cron/`@reboot`, …), добавьте префикс `taskset` внутрь того сценария или юнита, который его действительно запускает, иначе при перезапуске привязка потеряется.

**Проверьте, что привязка применилась** — выведите фактическую привязку работающих процессов:

```bash
taskset -cp "$(pgrep -f 'autorun/index.js')"   # autorun daemon
taskset -cp "$(pgrep -x spectrumserver)"       # spectrumserver
```

**Допустимые значения (для обоих переопределений):** список `taskset -c` (`2-3`, `0,2,4`, `0-2,5`) либо `none`/`off`/`unpinned` для отсутствия привязки. Всё некорректное игнорируется, и применяется автоматический вывод, поэтому опечатка никогда не заблокирует запуск.

> На Raspberry Pi / любой машине с ≤ 4 ядрами обычно не нужно ни то, ни другое — автоматический путь и так запускает оба процесса без привязки, что для небольшого однородного процессора и есть правильный выбор. Переопределение предназначено для более крупных машин, не являющихся гибридами Intel.

### Файлы и конечные точки

| Элемент | Назначение |
|---|---|
| `autorun.json` | Сохранённая конфигурация (идентификация, слоты, приёмники отчётов, максимум слотов, необязательное переопределение `cores`). Записывается вкладкой; игнорируется git. |
| `autorun-status.json` | Актуальное состояние, читаемое карточкой (pid, счётчики, последняя выгрузка). Записывается каждые 15 с; удаляется при остановке. |
| `frontend/dist/autorun-active.json` | Публичные данные значка, отдаваемые по `/autorun-active.json`. Пусто, когда отчётность выключена. |
| `autorun.log` | Стандартный вывод и ошибки службы. |
| `GET/POST /admin/api/autorun/config` | Чтение/запись `autorun.json` (проверяет позывной, локатор, комбинации диапазон/режим, предел слотов). |
| `GET /admin/api/autorun/status` | Состояние работы (`pgrep`) + `autorun-status.json`. |
| `POST /admin/api/autorun/start` / `stop` | Запуск (`taskset -c <auto> node autorun/index.js`) / `SIGTERM`. Диапазон ядер выводится из ЦП (см. выше). |

> **Примечание:** после обновления `admin_server.py` нужен [Перезапуск панели](#перезапуск-панели), чтобы загрузились новые маршруты autorun или обновлённая матрица диапазон/режим. Служба работает как отдельный процесс, поэтому переживает перезапуски панели администратора.

## Устранение неполадок

| Проблема | Решение |
|---|---|
| Панель администратора не запускается | Проверьте `admin.log` — обычно не хватает пакета Python |
| Прокси не запускается | Выполните `python3 -c "import aiohttp"` — при ошибке: `pip3 install aiohttp --break-system-packages` |
| `proxy.log` пуст | Сначала проверьте, действительно ли прокси работает (`./manage_admin.sh status`). Если да, у вас старая версия: лаунчер должен использовать `python3 -u` (без буферизации — иначе стартовый баннер никогда не покинет 8-КБ буфер), а `main()` в `proxy.py` должен вызывать `logging.basicConfig()` (иначе у журнала доступа aiohttp нет обработчика и каждая строка запроса теряется, поскольку `web.AppRunner`, в отличие от `web.run_app`, не настраивает журналирование). |
| Прокси запускается, но водопад пуст | Проверьте `sdr_host` в `admin_config.json` — обычно `127.0.0.1`. Если там остался старый локальный IP от прежней версии, исправьте его и выполните [Перезапуск панели](#перезапуск-панели) |
| Кнопка Kick сообщает «no connections» | Выполните `getcap $(which ss)` — если нет `cap_net_admin`, выполните `sudo setcap cap_net_admin+ep $(which ss)` |
| Состояние всегда OFFLINE | Перейдите в Settings → SDR Process Name — укажите точное имя, которое показывает `ps -eo comm,args \| grep -v grep` |
| Страница Users не показывает данных | Проверьте работу конечной точки: `curl http://127.0.0.1:<public_port>/users` |
| Внешний браузер получает NetworkError | Проверьте, работает ли прокси: `./manage_admin.sh status` |
| Прокси перестал работать после изменения сети | Актуально, только если в `sdr_host` всё ещё локальный IP — задайте `127.0.0.1` и выполните [Перезапуск панели](#перезапуск-панели) |
| Кнопка удаления чата не действует | Проверьте право записи в файл журнала чата: `ls -l ~/PhantomSDR-Plus/chat.jsonl` |
| Сообщение на водопаде не появляется | Убедитесь, что прокси работает (`./manage_admin.sh status`) и веб-интерфейс собран из свежей версии, включающей отрисовщик наложения |
| Сообщение на водопаде пропало после перезапуска | Так и задумано — состояние сообщения хранится только в памяти; отправьте его заново после перезапуска панели |
| «Start» в Spot Reporting не срабатывает / служба сразу завершается | Проверьте `autorun.log`. Обычно отсутствует символическая ссылка `autorun/node_modules` (`ln -sfn ../frontend/node_modules autorun/node_modules`) или не установлен `taskset` (`sudo apt install -y util-linux`). |
| Spot Reporting: служба работает, но `decodes` остаётся 0, а в `autorun.log` видно `504` / `tap closed 1006` | Аудиоотвод не может достучаться до spectrumserver. Служба определяет порт автоматически по конфигурации **работающего** сервера; строка журнала `[autorun] tap backend: HOST:PORT` должна совпадать с вашим `[server] port`. Если она неверна (или сервер не работал при запуске), задайте порт явно в `autorun.json`: `"server": { "host": "127.0.0.1", "port": 9002 }`, затем Stop→Start. |
| Spot Reporting показывает «0 sent» | Нормально в первые минуты — PSK Reporter отправляет каждые 5 мин, wsprnet — каждые 2 мин. Убедитесь, что включён приёмник отчётов и служба работает. |
| Новые диапазоны/режимы не появляются в матрице | [Перезапуск панели](#перезапуск-панели) — матрица загружается при старте. |
| В `autorun.log` видно `MODULE_TYPELESS_PACKAGE_JSON` / «Reparsing as ES module … performance overhead» | Косметическое предупреждение (декодирование работает). В `frontend/src/modules/package.json` отсутствует `"type": "module"`; добавьте эту строку ближе к началу, затем Stop→Start. Пересборка веб-интерфейса не нужна — служба импортирует исходный файл напрямую. |
| «Start» в Spot Reporting завершается с `taskset: … Invalid argument` на старом/слабом ПК | С учитывающим конфигурацию лаунчером такого быть не должно — диапазон ядер выводится из числа процессоров и на ≤ 4 ядрах привязка не применяется. Если это произошло, ваш `admin_server.py` старее этого изменения; обновите его (`_autorun_taskset_prefix`) и выполните [Перезапуск панели](#перезапуск-панели). |
| Значок REPORTING не появляется на водопаде | Отчётность должна быть включена хотя бы с одним слотом; значок читает `/autorun-active.json`. Пересоберите веб-интерфейс, если `dist/index.html` старее значка. |
